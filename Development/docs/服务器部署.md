# 服务器部署

这份文档只保留当前要走的这一条路：

**前端和后端继续跑在宿主机，只有 `william_algorithm/rag` 和 `william_algorithm/voice` 用 Docker 隔离。**

这样做的好处是：

- 不改你现在前后端的开发和部署方式
- 把最容易出环境问题的 Python 算法隔离起来
- backend 继续通过 HTTP 调 `rag` 和 `voice`

## 当前目标拓扑

```text
frontend (host)
   ↓
backend (host, :3001)
   ├─ http://127.0.0.1:8010 -> rag (docker)
   └─ http://127.0.0.1:8020 -> voice (docker)
```

重点：

- 前端不进 Docker
- backend 不进 Docker
- 只起两个容器：
  - `william-rag`
  - `william-voice`

## 关于 CentOS 7.9

CentOS 7 已经 EOL。短期可以用，但你要预期：

- 宿主机层面更老
- Docker 本身和系统库更容易出兼容问题
- 长期最好迁到 Rocky / Alma / Ubuntu

但只要你现在把 Python 算法放进容器里，环境问题会比裸装轻很多。

## 仓库里现在该用哪个 Docker 入口

直接用仓库根目录的：

```bash
docker-compose.yml
```

它现在默认只起算法服务：

- `rag`
- `voice`

## 一、服务器准备

### 1. 安装 Docker

CentOS 7 常见做法：

```bash
sudo yum install -y yum-utils device-mapper-persistent-data lvm2
sudo yum-config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo yum install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo systemctl enable --now docker
docker version
docker compose version
```

如果 `docker-compose-plugin` 装不上，说明仓库源或系统版本太旧，这本身就是 CentOS 7 的典型问题。那时要么换机器，要么装旧版 `docker-compose`。

### 2. 拉代码

```bash
mkdir -p /srv
cd /srv
git clone <你的仓库地址> william
cd /srv/william/William_Dev
```

## 二、配置算法容器环境

### 1. 准备 `.env.docker`

```bash
cp .env.docker.example .env.docker
```

然后编辑：

```env
OPENAI_API_KEY=你的真实 key
COHERE_API_KEY=

RAG_DEFAULT_EXPERT=li_songwei
RAG_PRELOAD_EXPERTS=li_songwei
RAG_LLM_MODEL=gpt-4o-mini
RAG_EMBEDDING_MODEL=text-embedding-3-large
```

如果你不用 `CohereRerank`，`COHERE_API_KEY` 留空就行。

### 2. 构建并启动算法容器

在仓库根目录执行：

```bash
docker compose build
docker compose up -d
```

查看状态：

```bash
docker ps
docker compose logs -f rag
docker compose logs -f voice
```

### 3. 健康检查

```bash
curl http://127.0.0.1:8010/health
curl http://127.0.0.1:8020/health
```

正常情况下：

- `rag` 监听 `127.0.0.1:8010`
- `voice` 监听 `127.0.0.1:8020`

它们只绑定本机，不直接暴露到公网。

## 三、宿主机上的 backend 怎么配

backend 不再负责给算法装环境，只负责调用它们。

在：

```bash
Development/backend/.env
```

至少保证这几项：

```env
RAG_SERVICE_URL=http://127.0.0.1:8010
RAG_SERVICE_AUTOSTART=false
RAG_SERVICE_WARMUP_ON_BOOT=false
RAG_SERVICE_ALLOW_LEGACY_FALLBACK=false

VOICE_SERVICE_URL=http://127.0.0.1:8020
VOICE_SERVICE_AUTOSTART=false
VOICE_SERVICE_WARMUP_ON_BOOT=false
```

这里要注意：

- `AUTOSTART=false`
- `WARMUP_ON_BOOT=false`

因为容器已经独立跑起来了，不要让 backend 再尝试在宿主机里起 Python 子进程。

## 五、更新发布时怎么做

如果你改的是：

- `william_algorithm/rag`
- `william_algorithm/voice`
- `docker/rag.Dockerfile`
- `docker/voice.Dockerfile`
- `docker-compose.yml`

那就重建算法镜像：

```bash
cd /srv/william/William_Dev
git pull
docker compose build
docker compose up -d
```

如果你只改了前后端：

- 不需要重建算法容器
- 只要重新部署宿主机上的 frontend/backend

## 六、最容易踩的坑

### 1. backend 还在试图自动拉起算法

如果 `.env` 里没关掉：

- `RAG_SERVICE_AUTOSTART`
- `VOICE_SERVICE_AUTOSTART`

backend 还是会尝试起本地 Python 进程，这和 Docker 方案冲突。

### 2. 端口被旧进程占用

算法容器用的是：

- `8010`
- `8020`

如果宿主机之前已经手工跑过 `rag` / `voice`，先关掉旧进程。

### 3. 第一次构建比较慢

原因是：

- Python 依赖安装
- 模型相关依赖准备

这属于正常现象。

### 4. CentOS 7 的 Docker/系统库问题

如果你发现：

- Docker 装不上
- compose 插件不可用
- 容器莫名其妙起不来

优先怀疑宿主机太旧，而不是先怀疑项目代码。

## 现在最容易踩的坑

### 1. `ffmpeg` 没装

表现：

- `voice` 起不来
- 音频转写失败
- `/transcribe` 或 `/analyze` 报错

先查：

```bash
ffmpeg -version
```

### 2. 服务器没法下载模型

表现：

- `rag` 或 `voice` 第一次启动卡很久
- Hugging Face / Whisper 模型下载失败

如果服务器外网受限，这会直接影响首次启动。

### 3. `.env` 没配完整

尤其是：

- `OPENAI_API_KEY`
- 数据库配置
- `RAG_SERVICE_PYTHON`
- `VOICE_SERVICE_PYTHON`

### 4. 以为 backend 会自动安装算法环境

不会。

backend 只负责：

- 调用
- 探活
- 自动拉起现成服务

不负责：

- 创建虚拟环境
- `uv sync`
- 下载模型
- 安装系统包

### 5. CentOS 7 自带环境太旧

表现：

- 某些 wheel 装不上
- 某些新依赖编译失败
- `ffmpeg` 很难装

如果你反复被环境卡住，不要一直怀疑项目代码，优先怀疑系统本身太旧。

## 我建议的运行方式

### 第一次部署

手工做完这几件事：

1. 系统依赖安装
2. conda 环境创建
3. `uv sync`
4. `.env` 配置
5. 手工验证 `rag` / `voice`

### 后续启动

再让 backend 去自动拉起算法服务。

这就是当前项目最稳的方式。

## 最后一句

如果你现在只是先验证能不能上线：

- 先不要追求“一键自动化部署”
- 先把环境稳定跑通
- 再考虑 systemd / nginx / pm2 这种常驻化

当前项目最怕的不是启动命令多，而是：

**算法环境没准备好，却误以为 backend 会自己搞定。**
